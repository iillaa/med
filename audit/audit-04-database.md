# 🗄️ Audit 04 — Database (JSON File-Based)
> Date: 2026-08-01 | Role: Database Architect | Mode: Audit-Only
> Note: This project uses JSON flat files as its database (cats_db.json, suggestions.json, pdf_index.json). Analysis is adapted accordingly.

---

## DB-01
- **File/table:** `cats_db.json` (144 KB, ~in-memory array)
- **Severity:** 🔴 CRITICAL
- **Problem:** Full database rewrite on every mutation — no partial update capability.
- **Evidence:** Every CAT create/edit/delete calls `safeWriteJsonAsync(DB_FILE, cache.catsCache)` which serializes the ENTIRE array to disk. At current size (144 KB), this is fast. But at 10× growth (1.4 MB), it becomes a blocking bottleneck — and the `dbLock` serializes all writes so concurrent admin actions queue up.
- **Performance estimate:**
  - 1K users: ✅ Fine (144 KB writes, sub-10ms)
  - 10K users: ✅ Acceptable (if DB grows to ~1.4 MB, writes take ~50ms)
  - 100K users: ❌ Problem (1 full rewrite per CAT edit, writes could take 500ms+, lock queue grows)
  - 1M users: ❌ Infeasible (JSON flat file approach breaks entirely)
- **Fix:** For current scale (medical student app, <1K users), no immediate action. Long-term: migrate to SQLite via `better-sqlite3`.

## DB-02
- **File/table:** `cats_db.json` — no schema validation at write time
- **Severity:** 🟠 HIGH
- **Problem:** Data written to the DB is only validated minimally (title + category required for new entries). Free-form text fields (`summary`, `ordonnance`, `red_flags`) accept any string of unlimited length — no max-length, no character sanitization. A malformed bulk-import could inject oversized strings that survive in the DB forever.
- **Evidence:** `server/routes/cats.js` line 164: only `title` and `category` are validated for existence. No length/format checks on other fields.
- **Performance estimate:** Not performance-related — data integrity issue.
- **Fix:** Add a `validateCatSchema()` function that enforces max lengths (e.g., summary ≤ 5000 chars, ordonnance ≤ 3000 chars) and runs at every write point.

## DB-03
- **File/table:** `pdf_index.json` (1.6 MB loaded fully into memory)
- **Severity:** 🟠 HIGH
- **Problem:** `pdf_index.json` is 1,640,252 bytes (~1.6 MB). It is loaded entirely into `cache.pdfIndex` on startup and kept in RAM. It is also returned in full via `GET /api/pdf-index` without authentication. Any user on any network can download the full 1.6 MB index with zero authentication.
- **Evidence:** `server/routes/search.js` line 156-176: no auth check on `GET /api/pdf-index`.
- **Performance estimate:**
  - 1K users: ✅ Memory fine, but 1.6 MB transfers per unauthenticated call is expensive
  - 10K users: 🟠 Serious bandwidth concern if many concurrent calls
- **Fix:** Require `x-app-key` header on `GET /api/pdf-index` (same as `/api/cats`), or serve only the incremental diff by default.

## DB-04
- **File/table:** `cats_db.json` — ID allocation race condition
- **Severity:** 🟠 HIGH
- **Problem:** New CAT IDs are generated by finding the current max ID and adding 1: `cache.catsCache.reduce((max, cat) => cat.id > max ? cat.id : max, 0) + 1`. This is inside a `dbLock.acquire()` call, so concurrent writes are serialized — no race condition. However, if two bulk-import operations run simultaneously, the second import sees the updated cache from the first and increments correctly. The pattern is safe BUT relies entirely on the `dbLock` being held for the full transaction.
- **Evidence:** `server/routes/cats.js` line 60 and `server/routes/suggestions.js` line 76.
- **Performance estimate:** Safe at any scale as long as the lock is maintained.
- **Fix:** No immediate fix needed; add a comment documenting why the lock must wrap the full ID allocation + write sequence.

## DB-05
- **File/table:** `suggestions.json` — no size cap on accumulated suggestions
- **Severity:** 🟠 HIGH
- **Problem:** Suggestions accumulate indefinitely. There is no maximum number of pending suggestions, no expiry for old/ignored suggestions, and no pagination on the admin review endpoint. If 10,000 suggestions accumulate (easily achievable via the unauthenticated POST endpoint), the admin UI becomes unusable and loading takes seconds.
- **Evidence:** `GET /api/suggestions` returns `cache.suggestionsCache` (the full array) to admin. No `.slice()`, no pagination, no limit.
- **Performance estimate:**
  - 100 suggestions: ✅ Fine
  - 1,000 suggestions: 🟠 Slow admin load (~250 KB JSON)
  - 10,000 suggestions: ❌ Admin UI hangs
- **Fix:** Add a cap of 500 pending suggestions (reject new ones when limit is reached), auto-expire suggestions older than 30 days, and paginate the admin endpoint.

## DB-06
- **File/table:** `cats_db.json` — `history` array grows forever per CAT
- **Severity:** 🟡 MEDIUM
- **Problem:** Every edit to a CAT appends to its `history` array: `cat.history.push({ timestamp, action, detail, previousState })`. There is no cap on history length. A heavily edited CAT (e.g., one updated 500 times by the AI generator) accumulates a massive embedded history array, inflating the DB file size and slowing the full-file write.
- **Evidence:** `server/routes/cats.js` line 137: `cat.history.push(...)` with no trim.
- **Performance estimate:** Individually small but cumulative over years.
- **Fix:** Cap history at the last 50 entries per CAT: `if (cat.history.length > 50) cat.history = cat.history.slice(-50);`.

## DB-07
- **File/table:** `data-store.js` — backup runs on startup AND every 12 hours
- **Severity:** 🟡 MEDIUM
- **Problem:** `runDatabaseBackup` is called immediately at startup (line 162) and then every 12 hours via `setInterval`. If the server restarts 10 times in a day (e.g., due to crashes with no PM2), 10 identical startup backups are created and the 10-file rotation discards the older useful backups. The rotation is by count, not by age — so 10 restart-backups within 1 hour replace the last 10 days of backups.
- **Evidence:** `server/index.js` lines 162-163.
- **Fix:** Skip the startup backup if a backup was already made within the last 6 hours (check mtime of the most recent backup file before creating a new one).
